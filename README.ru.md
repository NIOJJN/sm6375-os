# vv1raos

[English](README.md) | **Русский**

Автономное (bare-metal) ядро для AArch64, написанное на Rust.

vv1raos не зависит от Android или Linux. Это ядро `#![no_std]`, `#![no_main]` без внешних зависимостей от крейтов. Оно собирается на стабильном Rust и работает под QEMU (машина `virt`), а также ведётся работа по запуску на реальном железе: Qualcomm SM6375 (Snapdragon 695, «Blair») в Poco X4 Pro.

## Статус

| Область | Статус |
|---|---|
| QEMU `virt` (EL1 и EL2) | Работает |
| QEMU с фейковым DTB под SM6375 | Используется для отработки пути загрузки телефона (`make run-dtb`) |
| Реальное железо (Poco X4 Pro, SM6375) | Идёт процесс bring-up, сквозная проверка не завершена |
| Драйвер UFS | Реализован путь перехвата (takeover), **не тестировался на железе** |

## Возможности

- Загрузка AArch64: заголовок образа arm64, таблица векторов исключений, переход EL2 → EL1, вход вторичных CPU для PSCI `CPU_ON`
- Разбор Device Tree: RAM, зарезервированные и no-map регионы, GIC, таймер, PSCI, CPU, UART, watchdog, TLMM, initrd в `/chosen`
- Две консоли: PL011 (QEMU `virt`) и Qualcomm GENI SE UART (SM6375), с ранним выводом до включения MMU
- Watchdog APSS отключается при загрузке, если в DTB есть узел watchdog
- Identity-mapped ядро с W^X страницами, страничный аллокатор физической памяти, адресные пространства процессов с 8-битными ASID
- Пользовательское пространство в EL0: загрузчик ELF, системные вызовы через `svc #0`, demand paging в окне кучи, процессы с несколькими потоками
- Доступ к объектам ядра (endpoints, shared memory, ports) на основе capability с подсчётом ссылок и отзывом прав при смерти владельца
- Синхронный IPC (call/recv/reply, как в L4/seL4) с таймаутами, отменой и наследованием приоритетов; асинхронные порты с уведомлениями; futex, работающие между процессами через разделяемую память
- GICv3 с самотестом SGI, Generic Timer на 100 Гц
- SMP: до 4 ядер, запускаемых через PSCI `CPU_ON`, per-CPU состояние, IPI, приоритетный планировщик с вытеснением
- cpio `initramfs`; ядро передаёт управление `init` (PID 1) в EL0, который запускает сервисы, тесты и оболочку
- Модель платформенных устройств на основе DTB, драйверы регистрируются через `.init_array` (см. раздел «Модель платформенных драйверов»)
- Драйверы SM6375: GCC clocks, SPMI, PMIC, GENI UART, TLMM pinmux, Apps SMMU (обход SID), UFS, GPT, верификация дерева тактовых сигналов и вибромотор как индикатор для диагностики загрузки без консоли
- Обработчик исключений, выводящий регистры, backtrace по указателю кадра, слова стека и обход таблиц страниц упавшего процесса

## Требования

- Rust (stable) с:
  - таргетом `aarch64-unknown-none-softfloat`;
  - компонентом `llvm-tools` (Makefile находит `llvm-objcopy` в sysroot Rust).
- `make`.
- `qemu-system-aarch64` (для `run`, `run-el2`, `run-dtb`).
- `mkbootimg` (для `bootimg` и `bootimg-qemu`).

```sh
rustup target add aarch64-unknown-none-softfloat
rustup component add llvm-tools
```

Makefile ставит `~/.cargo/bin` первым в `PATH`, чтобы использовался `cargo` из rustup, а не системный, в котором нет bare-metal таргета (это важно на WSL).

## Сборка и запуск

| Цель | Что делает |
|---|---|
| `make build` | Собирает userspace (`user/`), затем ядро, затем конвертирует ELF в raw-образ `kernel.bin` |
| `make initramfs` | Собирает `initramfs.cpio` (компилирует и запускает `make_initramfs.rs` на хосте) |
| `make run` | Запуск в QEMU `virt` (GICv3, 4 CPU, 512 MiB) на EL1 |
| `make run-el2` | То же, но с `virtualization=on` для проверки перехода EL2 → EL1 |
| `make run-dtb` | Запуск в QEMU с `fake_sm6375.dtb` — DTB, повторяющим структуру реального SM6375 (см. `gen_fake_dtb.py`) |
| `make bootimg` | Собирает `boot.img` (header v4) для `fastboot boot boot.img` на Poco X4 Pro |
| `make bootimg-qemu` | Собирает `boot-qemu.img` (header v4) с базовым адресом QEMU `virt` `0x40000000` |

ELF ядра — `target/aarch64-unknown-none-softfloat/release/mk` (крейт называется `mk`). Release-сборки используют `opt-level = "s"`, LTO и `panic = "abort"`.

## Запуск на реальном устройстве

Цель: Poco X4 Pro (SM6375 / Blair).

- DDR начинается с `0x80000000`. Ядро загружается по адресу `0x80080000`: заголовок образа arm64 задаёт `text_offset = 0x80000`, а `make bootimg` использует `--base 0x80000000 --kernel_offset 0x80000`.
- Адрес загрузки по умолчанию в линкер-скрипте — `0x40080000` (QEMU `virt`). Он переопределяется через символ `__load_base`, задаваемый `LOAD_BASE`: используйте `LOAD_BASE=0x80080000 make bootimg`. `LOAD_BASE` должен быть кратен 2 MiB плюс `0x80000`.
- Device Tree берётся из `vendor_boot` устройства с патчем, включающим консольный GENI UART (`status = "okay"`).
- Образ запускается через `fastboot boot boot.img`, поэтому во флеш-память ничего не пишется.

> **Внимание:** загрузка на реальном железе экспериментальна. Перед попыткой убедитесь, что знаете, как восстановить устройство.

## Загрузка

### Точка входа (`src/boot.S`)

1. Маскируются все исключения (DAIF) и проверяется текущий уровень исключений; EL2 понижается до EL1 (`HCR_EL2.RW = 1`, доступ к счётчику включён, доступ к системным регистрам GICv3 включён), EL1 используется напрямую. Проверка MPIDR намеренно пропускается: у CPU0 в SM6375 `Aff1 = 1`.
2. На EL1: MMU и кэши выключены, настраивается стек, устанавливается `VBAR_EL1`, включаются FP/SIMD, очищается BSS, затем вызывается `kernel_main(dtb)`.
3. Вторичные ядра входят через `secondary_entry` (по PSCI `CPU_ON`), повторяют понижение EL2 → EL1, берут стек 32 KiB из `__secondary_stacks` (четыре слота по номеру CPU) и вызывают `secondary_main`.

Заголовок образа arm64 объявляет little-endian ядро со страницами 4 KiB.

### Этапы `kernel_main` (`src/main.rs`)

1. Инициализация загрузочного CPU, регистрация драйверов (`.init_array`), разбор DTB.
2. Отключение watchdog, подъём консолей UART.
3. Инициализация PMM (с резервированием ядра, DTB, no-map и reserved-memory регионов), включение MMU, самотест PMM.
4. Инициализация разделяемой памяти, портов, IPC и initramfs.
5. Платформенные устройства и probe драйверов, TLMM pinmux, вывод дерева тактовых сигналов.
6. GICv3 и самотест SGI, Generic Timer, планировщик.
7. Подъём SMP и самотест.
8. Запуск `init` (PID 1) и старт планировщика.

Фатальные ошибки инициализации (невалидный DTB, нет RAM, нет узла GICv3, `CNTFRQ_EL0 == 0`) логируются, и CPU останавливается в `wfe`.

### Раскладка образа ядра (`linker.ld`)

`.text` (с `.text.boot` в начале), `.rodata`, `.data`, `.init_array`, `.bss`, затем загрузочный стек 64 KiB; каждый выровнен на 4 KiB. `__image_size` — размер от `__kernel_start` до `__kernel_end`.

## Консоли

- **PL011** (QEMU `virt`): базовый адрес из DTB.
- **GENI SE UART** (SM6375): легаси-драйверы UARTDM (`uart.rs`, `msm_uart.rs`) на этом SoC не используются, так как каждый UART — это GENI serial engine внутри QUPv3. На Poco X4 Pro консольный узел — `/soc/qcom,qup_uart@4c8c000` (`compatible = "qcom,msm-geni-console"`). Драйвер предполагает, что XBL/ABL уже настроил движок в режиме UART с включёнными тактовыми сигналами; он только выбирает режим FIFO, очищает ожидающие прерывания и опрашивает путь TX. **Он работает только на передачу: приёма пока нет.**

Если присутствуют обе консоли, вывод идёт в обе (под QEMU это заодно проверяет путь GENI). `emergency_write` обходит блокировку консоли и используется обработчиками исключений и panic. Ввод идёт только с PL011: системный вызов `read` (используется оболочкой) ждёт на нём, поэтому ввода с клавиатуры на телефоне пока нет.

## Модель платформенных драйверов

Драйверы описывают себя структурой `Driver` (имя, до 8 строк `compatible`, `probe`) и регистрируются через конструктор, помещаемый в `.init_array` (это делает макрос `platform_driver!`). `kernel_main` запускает все конструкторы до разбора DTB.

- **Популяция:** платформенными устройствами становятся только узлы DTB, чей `compatible` совпадает с зарегистрированным драйвером. В реальном DTB SM6375 сотни таких узлов, а реестр ограничен (32 драйвера, 64 устройства), поэтому фильтр не даёт реестру заполниться устройствами, которые никто не обслуживает.
- **Ресурсы:** регионы памяти, IRQ, именованные тактовые сигналы, power domains и stream ID для IOMMU.
- **Отображение MMIO:** перед `probe` каждый регион памяти устройства отображается как device memory identity-маппингом, так как регионы вроде GCC, SPMI и UFS отсутствуют в списке MMIO на этапе загрузки.
- **Порядок probe:** устройства пробуются в порядке регистрации из DTB. Разрешения зависимостей и отложенного probe нет. Неудачный probe логируется (`platform: probe failed for <name>: <error>`), и устройство помечается как failed.

## Внутреннее устройство ядра

### Память

- **Таблицы страниц:** гранулярность 4 KiB, 48-битное VA, только `TTBR0` (`EPD1 = 1`), identity-маппинг (VA == PA), блоки по 2 MiB где возможно. Образ ядра отображается с W^X: текст — read-execute, rodata — read-only, data и BSS — read-write и non-executable. Вся RAM — Normal write-back и non-executable.
- **Device memory:** всё ниже первого банка RAM (с ограничением 4 GiB) отображается как Device-nGnRnE. Регионы, помеченные в DTB как `no-map`, размапливаются, если не пересекаются с образом ядра. Device-регионы, найденные позже платформенным слоем, маплятся в живые таблицы через `map_device_identity`.
- **PMM:** bump-указатель по основному диапазону RAM плюс односвязный список свободных страниц. Пропускает до 256 зарезервированных диапазонов (образ ядра, DTB, `no-map` и весь `/reserved-memory`, которого на SM6375 около 20 регионов). Страницы обнуляются при выделении. `alloc_contiguous` обслуживает большие буферы, такие как initramfs.
- **ASID:** 8-битные, от 1 до 255 для процессов, 0 для ядра. Переиспользуются после 255 адресных пространств, поэтому при переключении на переиспользованный ASID его TLB-записи инвалидируются на всех ядрах.

### Процессы и адресные пространства

У каждого процесса своя таблица L0 и копия L1-таблицы ядра. Его пользовательское окно — одна запись L1 (1 GiB), начиная с `0x40_0000_0000`:

| Диапазон (смещение от `USER_BASE`) | Использование |
|---|---|
| `0x00_0000`–`0x07_0000` | Образ ELF (`ET_EXEC`, AArch64, сегменты `PT_LOAD`) |
| ниже `0x08_0000` | Стек главного потока, 16 страниц, вершина на `USER_BASE + 0x80000` |
| `0x10_0000`–`0x20_0000` | Окно разделяемой памяти |
| `0x20_0000`–`0x1000_0000` | Анонимная память: куча и стеки потоков |

Страницы, принадлежащие процессу, несут программный бит (бит 55) и освобождаются при уничтожении адресного пространства. Страницы разделяемой памяти и MMIO не помечаются, так как у них свои счётчики ссылок. `copy_from_user` и `copy_to_user` обходят таблицы страниц процесса вместо разыменования пользовательских адресов, причём последний пишет только в страницы, доступные процессу на запись.

Ошибка из EL0 внутри анонимного окна разрешается demand paging. Любая другая ошибка убивает процесс с кодом выхода 255.

Лимиты процессов (`proc.rs`): 8 процессов, 8 потоков на процесс, 16 capability на процесс, 32 маппинга на процесс. Завершённый дочерний процесс остаётся зомби, пока родитель не заберёт код выхода через `wait`; сироты собираются автоматически.

### Планировщик и SMP

- До 32 потоков ядра; слоты 0–3 — idle-потоки на каждое ядро. У каждого потока стек ядра 128 KiB.
- Приоритеты 0–7 (по умолчанию 3). Процесс не может поднять поток выше своего `max_prio`. Сервер, обрабатывающий запрос, временно наследует приоритет клиента.
- Квант времени 5 тиков (50 мс при 100 Гц). Одна глобальная блокировка планировщика защищает таблицу потоков, а каждое ядро хранит свой текущий поток, `TTBR0` и ASID в per-CPU структуре.
- Переключение контекста в два шага: уходящий поток становится `Switching` и становится `Ready` только после сохранения указателя стека, чтобы другое ядро не подхватило его слишком рано.
- Ядро вытесняет только при возврате в EL0 (и в своих точках планирования — idle, sleep, IPC), но никогда посреди кода EL1.
- `wake`, пришедший до того, как поток заблокировался, запоминается, поэтому пробуждения не теряются на SMP.
- IPI используют SGI 2 (`IPI_RESCHED`). Только CPU0 продвигает глобальный счётчик тиков.
- Используется не более 4 ядер (`MAX_CPUS = 4`, берутся первые четыре узла `cpu@` из DTB). В SM6375 8 ядер.
- Блокировки: `SpinLock` маскирует IRQ на текущем ядре, пока удерживается. `IrqGuard` — критическая секция одного ядра.

### Объекты и capability

Все объекты ядра живут в одной таблице на 256 записей (endpoint, shared memory, MMIO, port) с типом, PID владельца и счётчиком ссылок. Процесс достигает объекта только через capability в своей таблице: ID объекта плюс права (`SEND`, `RECV`, `MAP`, `GRANT`). Права проверяются при каждом системном вызове, а тип объекта — через таблицу, поэтому его нельзя подделать. Capability можно передать в IPC-сообщении, только если у неё есть `GRANT`, и получатель получает её без `GRANT`. Когда процесс умирает, все capability других процессов на его объекты отзываются, а его объекты уничтожаются.

### IPC

- **Синхронный (endpoints):** рандеву `call`, `recv`, `reply`. Сообщение — 4 слова, до 1024 байт данных и не более одной capability. Ядро само заполняет PID отправителя, поэтому его нельзя подделать. Ожидание может завершиться по таймауту, по `cancel` из другого потока или из-за смерти партнёра. Есть 16 endpoints, у каждого очередь отправки на 8.
- **Асинхронный (ports):** `port_send` ставит сообщение в очередь (очередь на 8, при заполнении возвращается `ERR_AGAIN`), `port_notify` посылает сигнал без полезной нагрузки, а `port_recv` возвращает любое из них, с PID отправителя 0 для уведомления. Есть 16 портов.
- **Futex:** `futex_wait` и `futex_wake` используют в качестве ключа физический адрес 32-битного слова, поэтому работают между процессами через разделяемую память. Регистрация в качестве ожидающего и перепроверка значения происходят под одной блокировкой, что исключает потерянное пробуждение на SMP.

### Системные вызовы

`svc #0` из EL0. Номер — в `x8`, аргументы — в `x0`–`x4`, статус возвращается в `x0` (0 — успех, иначе код ошибки из `ipc.rs`). Дополнительные результаты — в `x1` и далее. IPC-сообщения передаются как структура `UMsg` на 64 байта в памяти процесса.

| Группа | Вызовы |
|---|---|
| Базовые | `YIELD` (0), `WRITE` (1), `EXIT` (2), `GETPID` (3), `SLEEP` (4), `TICKS` (5), `GETTID` (18), `READ` (28) |
| IPC | `CALL` (6), `RECV` (7), `REPLY` (8), `EP_CREATE` (13), `CANCEL` (21) |
| Память | `SHM_CREATE` (12), `SHM_MAP` (9), `MAP_ANON` (14), `UNMAP` (15) |
| Потоки | `THREAD_CREATE` (16), `THREAD_EXIT` (17), `SET_PRIO` (22), `FUTEX_WAIT` (19), `FUTEX_WAKE` (20) |
| Порты | `PORT_CREATE` (24), `PORT_SEND` (25), `PORT_RECV` (26), `PORT_NOTIFY` (27) |
| Capability | `CAP_DROP` (23) |
| Процессы | `SPAWN` (37), `WAIT` (38) |
| Статистика | `MEM_STATS` (39), `KSTATS` (40) |

`EXIT` завершает весь процесс, `THREAD_EXIT` — только вызывающий поток. `WRITE` ограничен 256 байтами и предваряет вывод PID.

### initramfs

Ядро находит ramdisk через `/chosen` (`linux,initrd-start` и `linux,initrd-end`), копирует его в физически непрерывную память из PMM и разбирает как cpio-архив `newc`.

- gzip принимается, но только если deflate-поток использует stored (несжатые) блоки; сжатые блоки отклоняются.
- Архив разворачивается в статический буфер 64 MiB.
- До 32 файлов, имена до 63 байт. Пустые файлы пропускаются.
- `spawn` ищет `bin/<name>`, затем `<name>`, затем `sbin/<name>`.

## Драйвер UFS (SM6375)

> **Статус: переписан, не проверен на железе.**

### Режимы работы

- **Takeover (по умолчанию):** если загрузчик уже поднял UFS (`HCE = 1`, `HCS.DP = 1`), ядро не трогает PHY, `HCE` и линк. Оно останавливает оставленные загрузчиком списки запросов и устанавливает свои. Это основной путь для `fastboot boot`.
- **Полная инициализация (fallback, `FORCE_FULL_INIT = true` или контроллер не поднят):** инициализация PHY, цикл `HCE`, `DME_LINKSTARTUP` (3 попытки). Последовательность PHY — минимальная, непроверенная последовательность регистров; нужны реальные таблицы QMP v4 из Linux (`phy-qcom-qmp-ufs`), поэтому этот путь, скорее всего, пока не заработает на реальном железе.

Все структуры UFSHCI (UTRD, UPIU, PRDT) написаны под UFSHCI 3.0 и Linux `ufshci.h`/`ufs.h` по памяти и не тестировались на устройстве.

### Последовательность probe

1. Маппинг ресурса HC (и PHY, по умолчанию `0x4807000`); драйвер соответствует `qcom,ufshc` и `qcom,ufs-qcom`.
2. Включение тактовых сигналов `core`, `bus` и `phy` через драйвер GCC SM6375 (сбои не фатальны, загрузчик мог их включить), затем проверка дерева тактовых сигналов.
3. Запрос обхода SMMU для stream ID контроллера — до любого DMA.
4. Takeover или полная инициализация (см. выше), затем контроллеру передаются собственные списки запросов ядра.
5. В режиме takeover, если `TEST UNIT READY` на LUN 0 уже успешен, инициализация устройства пропускается. Иначе: `NOP OUT`, установка `fDeviceInit` и ожидание его сброса, затем `TEST UNIT READY`.
6. `READ CAPACITY(10)` даёт число блоков и размер блока.
7. `ufs: probe ok`, затем запускается `gpt_init()`.

### Компоненты

| Компонент | Статус | Примечания |
|---|---|---|
| Путь takeover | ⏳ | Реализован; не тестировался на железе |
| Инициализация UFS PHY (QMP v4) | ❌ | Минимальная последовательность, **непроверена**; нужны реальные таблицы |
| Link startup | ⏳ | `DME_LINKSTARTUP` с повторами; не тестировался |
| Инициализация устройства | ⏳ | `NOP OUT` + query-флаг `fDeviceInit`; не тестировалось |
| SCSI `READ(10)` | ⏳ | Реализован; не тестировался на железе |
| SCSI `READ CAPACITY(10)` | ⏳ | Ёмкость и размер блока читаются при probe; не тестировалось на железе |
| API блочного устройства | ✅ | `ufs_read_sectors`, `ufs_get_capacity`, `ufs_block_size` |
| GPT (поиск ESP) | ⏳ | Запускается после успешного probe; см. GPT |
| initramfs из UFS | ⏳ | Планируется: загружать cpio из UFS вместо RAM |
| SCSI `WRITE(10)` | ❌ | Не реализован |

### Замечания по дизайну и ограничения

- Используется только **LUN 0**.
- Одновременно используется один слот запроса (слот 0) под спинлоком; завершение опрашивается по регистру doorbell. Список управления задачами не используется.
- Область DMA (список запросов, дескриптор команды, PRDT и буфер данных 16 KiB) — статическая структура с выравниванием на 4 KiB. Чтения разбиваются на куски, помещающиеся в буфер 16 KiB.
- Буферы предполагаются identity-mapped (VA == PA) и кэшируемыми (Normal WB), поэтому вокруг DMA выполняется обслуживание кэша (`dc civac`).
- `READ(10)` и `READ CAPACITY(10)` используют 32-битные LBA.

### API

```rust
/// Логический размер блока LUN 0 в байтах (обычно 4096); 0, если UFS не готов.
pub fn ufs_block_size() -> usize

/// Ёмкость LUN 0 в логических блоках.
pub fn ufs_get_capacity() -> Result<u64, DriverError>

/// Прочитать `count` логических блоков LUN 0 начиная с `lba` в `buf`.
/// `buf` должен вмещать минимум `count * ufs_block_size()` байт.
/// Возвращает число прочитанных байт.
pub fn ufs_read_sectors(lba: u64, count: u16, buf: &mut [u8]) -> Result<usize, DriverError>
```

`ufs_read_sectors` возвращает `NotReady` до успешного probe и `InvalidArg` при `count == 0`, слишком маленьком буфере или диапазоне за концом устройства.

Пример (устройство с логическими блоками 4096 байт):

```rust
let mut buf = [0u8; 4096];
// Прочитать один логический блок (4 KiB) по LBA 0
let n = ufs_read_sectors(0, 1, &mut buf)?;
assert_eq!(n, 4096);
```

### GPT

`gpt_init()` запускается после успешного probe UFS. Он нужен, чтобы ядро могло найти свой initramfs на UFS, не полагаясь на `initrd-start`/`initrd-end` загрузчика в `/chosen`.

- Читает заголовок GPT по LBA 1 и проверяет сигнатуру `EFI PART`. Несовпадение CRC заголовка только логируется, так как некоторые загрузчики его не обновляют.
- Требует записи разделов по 128 байт и размер блока UFS от 128 до 4096 байт. LBA — в логических блоках устройства.
- Сканирует массив записей в поисках EFI System Partition (GUID типа `C12A7328-F81F-11D2-BA4B-00A0C93EC93B`) и кэширует первое совпадение. Другие типы разделов пока не ищутся.
- API: `gpt_find_esp()`, `gpt_esp_info()` (первый LBA и размер в блоках), `gpt_read_esp(lba_offset, count, buf)`.
- Логирует `gpt: ESP found at LBA <first>..<last> (<n> MiB)` или `gpt: ESP not found: <reason>`.

### Интеграция с initramfs

**Текущая схема (RAM):**

1. Загрузчик размещает `initramfs.cpio` в RAM (ramdisk в `boot.img` или `-initrd` под QEMU).
2. Ядро разбирает cpio-архив из RAM в `initramfs::init()`.
3. Файлы загружаются через загрузчик ELF.

**Планируемая схема (UFS):**

1. Ядро находит раздел initramfs через GPT (сейчас — ESP).
2. Оно читает заголовок cpio из UFS через `ufs_read_sectors()` и проверяет магию `070701` (newc).
3. Файлы загружаются из UFS по требованию.

### Требования к Device Tree

Загрузчик должен предоставить DTB, в котором узлы UFS включены.

```dts
ufshc@4804000 {
    compatible = "qcom,ufshc";
    reg = <0x4804000 0x3000>;
    interrupts = <GIC_SPI 356 IRQ_TYPE_LEVEL_HIGH>;
    clocks = <&gcc GCC_UFS_CORE_CLK>,
             <&gcc GCC_UFS_AXI_CLK>,
             <&gcc GCC_UFS_PHY_CLK>;
    clock-names = "core", "bus", "phy";
    status = "okay";
};

ufsphy_mem@4807000 {
    compatible = "qcom,ufs-phy-qmp-v4";
    reg = <0x4807000 0xddc>;
    clocks = <&gcc GCC_UFS_PHY_CLK>;
    status = "okay";
};
```

> В оригинальном DTB оба узла имеют `status = "disabled"`. Загрузчик должен их пропатчить или передать исправленный DTB.

### Тестирование

**QEMU (`virt`):** UFS не пробуется (в DTB нет узла). initramfs загружается из RAM, самотест `stage 8 OK` проходит.

**Железо:**

1. Загрузчик включает UFS в DTB.
2. Ядро пробует драйвер и печатает `ufs: HC at <base>, size=<size>, PHY at <base>`.
3. В режиме takeover лог показывает `ufs: HC already up (HCE=1, DP=1), taking over`.
4. В режиме полной инициализации: `ufs: PHY init done (unverified)`, `ufs: HC enabled`, `ufs: link startup complete`.
5. `ufs: LUN 0: <blocks> blocks x <size> bytes`, затем `ufs: probe ok`, затем строка `gpt:`.
6. initramfs читается из раздела через `ufs_read_sectors()` (планируется).

### Отладка

Ожидаемые строки лога:

```text
ufs: HC at <base>, size=<size>, PHY at <base>
ufs: HC already up (HCE=1, DP=1), taking over      (режим takeover)
ufs: full HC init                                  (режим полной инициализации)
ufs: PHY init done (unverified)
ufs: HC enabled
ufs: link startup complete
ufs: LUN 0: <blocks> blocks x <size> bytes
ufs: probe ok
gpt: ESP found at LBA <first>..<last> (<n> MiB)
```

Другие полезные сообщения: `ufs: doorbell busy`, `ufs: NOP OUT failed`, `ufs: fDeviceInit did not clear`, `ufs: request failed, OCS=<n>`, `ufs: fatal error, IS=<n>`.

Полезные регистры UFSHCI:

| Регистр | Смещение | Значение |
|---|---|---|
| `IS` | `0x20` | Статус прерываний (`ULSS` = link startup, `UTRCS` = transfer complete) |
| `HCS` | `0x30` | Статус хост-контроллера (`UCRDY` = UIC command ready) |
| `HCE` | `0x34` | Включение хост-контроллера; после включения должен читаться `1` |
| `UTRLDBR` | `0x58` | Регистр doorbell; бит 0 = активен слот 0 |

Ранняя консоль для отладки (GENI UART на SM6375, по адресу `0x4c8c000` на Poco X4 Pro):

```rust
crate::drivers::geni_uart::early_init(0x4c8c000);
kprintln!("UFS: starting probe...");
```

Если ядро падает, `exception_handler` печатает вектор исключения, `ESR`, `ELR`, `FAR`, регистры, backtrace по указателю кадра, слова стека и обход таблиц страниц упавшего процесса, затем останавливается. Индикатор на вибромоторе (`vibro`) сигнализирует этапы загрузки на устройстве без консоли.

### Дорожная карта

- Проверить probe и путь takeover на железе.
- Заменить непроверенную последовательность PHY на реальные таблицы QMP v4 из Linux.
- GPT: искать произвольные разделы, а не только ESP.
- Загрузка файлов из cpio по требованию (не грузить весь initramfs в RAM).
- SCSI `WRITE(10)` для персистентности (логи, конфигурация).
- Приём данных на GENI консоли.
- Использовать все 8 ядер SM6375 (`MAX_CPUS` равен 4).
- Поддержка сжатого (deflate) gzip для initramfs.
- READ CAPACITY.
- Поиск GPT ESP.
